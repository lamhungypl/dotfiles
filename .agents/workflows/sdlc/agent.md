# E2E Project Architecture — Agent Onboarding

Read this file before writing any test or page object. It is the complete onboarding doc.

## Stack

- `@playwright/test ^1.50`
- TypeScript strict mode
- pnpm package manager
- Node 22
- Nx monorepo workspace

## Project Root

Read `workspaces.json` at the **workspace root** to resolve absolute paths:

```json
{
  "project": "TB",
  "workspace": "/absolute/path/to/teams-board",
  "e2e": "/absolute/path/to/teams-board/apps/teams-board-web-fe-e2e",
  "frontend": "/absolute/path/to/teams-board/apps/teams-board-web-fe"
}
```

| Field | Purpose |
|-------|---------|
| `project` | Project key — ID prefix for all backlog items (`TB-001`, `TB-002`…). Stable across all releases. |
| `workspace` | Absolute path to the monorepo root |
| `e2e` | Absolute path to the E2E app (`apps/teams-board-web-fe-e2e`) |
| `frontend` | Absolute path to the React SPA (`apps/teams-board-web-fe`) |

`workspaces.json` is gitignored and developer-local. A template is at `agents/workspaces.example.json`.
If it is missing, ask the user to create it from the example before proceeding.

## Test Commands

Run from the **workspace root**:

```bash
# Run all E2E tests (auto-starts dev server)
pnpm exec nx run @lhypl/teams-board-web-fe-e2e:e2e

# Run a specific test by ID
pnpm exec nx run @lhypl/teams-board-web-fe-e2e:e2e --grep "\[TB-001\]"

# Run tests in a feature directory
pnpm exec nx run @lhypl/teams-board-web-fe-e2e:e2e --grep "tasks"

# Run with visible browser
pnpm exec nx run @lhypl/teams-board-web-fe-e2e:e2e --headed
```

Alternatively, from the `apps/teams-board-web-fe-e2e` directory:

```bash
pnpm exec playwright test
pnpm exec playwright test --grep "\[TB-001\]"
```

## Base Configuration (`playwright.config.ts`)

- **Base URL**: `http://localhost:4200` (override with `BASE_URL` env var)
- **Timeout**: 5 minutes per test, 60s for actions and navigation
- **Test dir**: `src/e2e/`
- **Setup dir**: `src/setups/`
- **Projects**:
  - `setup` — auth setup (must run first)
  - `chromium` — all `*.spec.ts` tests, depends on setup

## Authentication

Auth state is pre-generated by `src/setups/auth.setup.ts` and stored as:
- `.auth/user.json` — primary user (alice@example.com / alice123)
- `.auth/user-bob.json` — secondary user for RBAC/multi-user tests (bob@example.com / bob123)

The setup file logs in via the UI using credentials from env or the defaults above.

## AppPage Interface (`src/app.page.ts`)

Every Page Object Model must implement this interface:

```typescript
export interface AppPage {
  goto: () => Promise<void>;               // Navigate to the page URL
  verifyPageAccessible: () => Promise<void>; // Assert page is accessible + key elements visible
  getStarted: () => Promise<void>;         // goto() + wait until ready for interaction
}
```

## Fixture Chain

### Base fixtures (`src/modules/permissions/permissions.fixtures.ts`)

```typescript
import { permissionsFixtures } from 'modules/permissions/permissions.fixtures';
// Provides: authenticatedPage (AuthenticatedPage) — uses .auth/user.json
```

### Feature fixtures pattern

Feature fixtures extend `permissionsFixtures`:

```typescript
import { permissionsFixtures } from 'modules/permissions/permissions.fixtures';
import { MyFeaturePage } from './my-feature.page';

export const myFeatureFixtures = permissionsFixtures.extend<{
  myFeaturePage: MyFeaturePage;
}>({
  myFeaturePage: async ({ authenticatedPage }, use) => {
    await use(new MyFeaturePage(authenticatedPage.page));
  },
});
```

## Module Structure

Each feature lives in `src/modules/{feature}/`:

```
src/modules/{feature}/
  {feature}.page.ts        ← Page Object (implements AppPage)
  {feature}.fixtures.ts    ← fixture chain (extends permissionsFixtures)
```

## Test File Location

## Selector Convention

1. `getByRole()` — preferred (semantic, accessible)
2. `getByLabel()` — preferred for form elements
3. `getByText()` — for visible text content
4. `.locator('[data-testid="..."]')` — when semantic selectors are ambiguous
5. CSS class patterns — last resort fallback

Never use positional selectors like `nth-child` or XPath unless absolutely unavoidable.

## Test Naming Convention

```typescript
test('[TB-001] description of expected behavior', async ({ ... }) => {
```

- `TB-NNN` matches the `id` field in `backlog.json`
- Description is in present tense: "shows error message when…", "navigates to…"
- One assertion focus per test

## Test Structure Pattern

```typescript
import { expect } from '@playwright/test';
import { myFeatureFixtures } from '../../modules/my-feature/my-feature.fixtures';

const test = myFeatureFixtures;

test.describe('My Feature', () => {
  test('[TB-001] navigates to correct URL on load', async ({ myFeaturePage }) => {
    await myFeaturePage.getStarted();
    await expect(myFeaturePage.page).toHaveURL(/\/tasks/);
  });
});
```

## What Agents Should NOT Do

- Do not modify `.auth/` or auth state files
- Do not modify `playwright.config.ts` unless adding a new project
- Do not create tests in `src/modules/` — tests live in `src/e2e/`
- Do not use `page.waitForTimeout()` — use `waitForURL`, `waitForSelector`, or expect assertions
- Do not hardcode credentials — use the seeded defaults (`alice@example.com`, `bob@example.com`)
- Do not touch `pnpm-lock.yaml` or `nx.json` unless explicitly instructed
